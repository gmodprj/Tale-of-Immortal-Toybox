# 05. 편집기 v0.1

> 작성일: 2026-10-12 · 대상 게임 버전: v1.2.113.259 · 모드 ID: `sWP6UL`

## 1. 범위

`docs/04-ingame-state-analysis.md` 15절의 1~3단계에서 쓰기가 실측된 기능만 넣었다.

| 탭 | 기능 | 쓰기 경로 |
|---|---|---|
| 능력치 | 능력치 39종의 저장값, 적용값(보정 포함), 허용 범위 표시. `-` / `+` / `최대`로 변경. 자원 회복 | `PropertyData`의 필드 대입. 쓰기 전에 `g.conf.roleAttributeLimit` 범위 검사 |
| 자원 | 영석 추가, 아이템 ID(숫자판 입력)와 수량으로 지급 | `WorldUnitData.RewardPropMoney`, `RewardPropItem` |
| 경지 | 현재·다음 경지와 수련치 표시. 수련치 채우기, 다음 단계로 돌파(소경지만) | `PropertyData.AddExp`, `UnitActionRoleUpGrade` |
| NPC | 가까운 순 NPC 목록(쪽 넘김), 선택, 호감도 변경(양쪽 함께), 그 NPC를 능력치 편집 대상으로 | 양쪽 `RelationData.SetIntim` |
| 안전 | 세이브 백업 상태와 수동 백업, 이번 실행의 변경 이력 | — |

넣지 않은 것: 영석 감소, 4단계 고위험 항목(NPC 생성·삭제, 문파, 시간, 이동, 전투).

2026-10-12 추가: 능력치 직접 입력(저장값 칸을 눌러 항목을 고르고 숫자를 입력해 적용)과 NPC 이름 검색(이름의 일부로 걸러 냄).

## 2. 사용법

- **Insert** 키로 창을 열고 닫는다. `%USERPROFILE%\AppData\LocalLow\guigugame\guigubahuang\TlToybox\config.txt`의 `hotkey=` 값을 `F2`나 `F3`으로 바꿀 수 있다(게임 재시작 후 적용).
- 값은 `단위` 버튼으로 증감 폭(1, 10, 100, 1000, 10000)을 고른 뒤 `-` / `+`로 바꾼다.
- 능력치를 숫자로 직접 넣으려면 저장값 칸을 누른 뒤 아래 입력 칸에 숫자를 쓰고 `적용`을 누른다.
- NPC 탭의 `이름 검색`에 이름의 일부를 쓰고 `검색`을 누르면 그 글자가 들어간 NPC만 가까운 순으로 나온다.
- 세이브에 진입한 뒤에만 쓸 수 있다.

## 3. 안전 규칙

| 규칙 | 구현 |
|---|---|
| 쓰기 전 백업 | 한 실행에서 첫 쓰기 직전에 세이브 폴더(`Steam\CacheData`)를 `TlToybox\backups\<시각>\`으로 복사한다. 백업에 실패하면 쓰지 않는다 |
| 범위 검사 | 능력치는 게임의 상한표 범위 밖이면 거부하고 사유를 표시한다. 게임은 저장값을 검증하지 않으므로 편집기가 막는다 |
| 재조회 | 쓴 직후 다시 읽어 기대값과 같은지 확인하고, 다르면 이력에 "재조회 불일치"로 남긴다 |
| 변경 이력 | 모든 쓰기를 "변경 전 -> 변경 후"로 창과 `TlToybox\changes.log`에 기록한다 |
| 경지 | 경지 ID를 직접 쓰지 않는다. 정식 돌파 행동만 호출한다 |
| 호감도 | 양쪽 값을 함께 쓴다. 범위는 편집기 자체 제한 -300~300이다(게임의 유효 범위는 미확인) |
| 수명 | 게임의 상한표에 상한이 없어 편집기 자체 상한 100000을 둔다 |

백업은 디스크에 저장된 세이브의 사본이다. 저장하지 않은 진행은 백업에 들어 있지 않다.

## 6. 알려진 한계

- 돌파 결과 창 같은 게임의 팝업이 편집기 창 뒤에 뜬다. 편집기를 닫아야 누를 수 있다.
- 창이 열려 있는 동안 값이 게임 쪽에서 바뀌어도 자동으로 갱신되지 않는다. 탭을 다시 누르면 갱신된다.
- 글꼴은 게임의 고딕체(`heiti`)를 우선해 빌려 쓴다. 처음에는 "처음 찾은 글꼴"을 썼더니 붓글씨체가 걸려 비슷한 글자(봉/붕)를 구분하기 어려웠다.
- 입력 칸에 글자를 치는 동안 게임의 단축키가 함께 반응하는지는 확인하지 못했다.
- 한글 입력기로 이름을 입력하는 것은 자동으로 시험할 수 없어 확인하지 못했다.
- 능력치는 공격 외 항목을 개별로 저장·재시작 검증하지 않았다. 같은 구조라는 점과 재조회 일치로만 확인한다.
- 가방이 가득 찼을 때의 지급 동작은 시험하지 않았다. 수량이 기대와 다르면 메시지로 알린다.
- 배포 빌드를 게임에 실어 보지는 않았다. 검증은 개발 빌드로 했다.

## 7. 공법 탭 (2026-10-12 추가)

편집 대상(플레이어 또는 NPC)이 익힌 공법을 보여 주고, 선택한 공법의 옵션을 편집한다.

| 기능 | 쓰기 경로 | 규칙 |
|---|---|---|
| 옵션 품질 `-` / `+` / `최고` | `MartialData.SetPrefixLevel` | 품질 단계 1부터 `ConfBattleSkillPrefixValue.GetPrefixMaxLevel`까지만 허용 |
| 옵션 `교체` | `MartialData.SetPrefixID` 후 `SetPrefixLevel` | 그 공법에 붙을 수 있는 옵션(`GetItems(skillType, baseID)`)만 보여 준다. 자리별 가중치가 0인 옵션, 중복 한도(`multi`) 초과, 선행·배타 조건(`require`) 위반은 사유와 함께 막는다 |
| 숙련 경험치 추가 | `UnitInfoData.AddMartialExp` | 게임이 올리지 않으면 그렇다고 알린다 |

조사로 확인한 구조:

- 옵션에 저장되는 수치(`prefixLevel`)는 게임이 품질 단계(`SkillPrefixData.level`)로 환산한다. 환산 기준은 옵션마다 달라서(시험한 옵션은 100과 199 사이, 200과 299 사이, 300과 399 사이에서 단계가 바뀜) 편집기는 고정 공식을 쓰지 않고 게임의 환산 결과를 이분 탐색해 원하는 단계의 가장 높은 수치를 찾는다.
- 게임은 수치를 검증하지 않는다. 한도를 넘는 수치를 쓰면 단계가 한도를 넘는다(한도 3인 옵션에 999를 쓰자 단계 6). **수치 -1은 값 배열의 구분자와 같아서 쓰면 옵션 해석이 어긋난다.** 편집기는 단계로만 받고 음수를 쓰지 않는다.
- `require`가 양수면 그 번호의 옵션이 함께 있어야 하고, 음수면 그 번호의 옵션과 함께 둘 수 없다. 설정 표의 사례(혈인 중첩 6번과 그 강화 옵션 8~10번, 6번과 7번의 배타)로 해석한 것이며 게임 코드로 확인한 것은 아니다.
- 공법의 이름은 옵션 구성에서 다시 계산된다. 옵션 1을 5번에서 1번으로 바꾸자 이름이 "파호수령술"에서 "연봉수령술"로 바뀌었다.

검증(게임에서 버튼으로 실행, NPC 유기정의 공법 대상):

| 시험 | 결과 |
|---|---|
| 옵션 1 품질 `+`, `최고`, `-` | 1 → 2 → 3 → 2. 한도(3)에서 `+`와 `최고` 버튼이 비활성 |
| 옵션 교체 화면 | 붙을 수 있는 옵션 16개 표시. 중복 한도 초과 2개, 자리 불가 4개가 사유와 함께 막힘 |
| 옵션 1을 1번으로 교체 | 5번 → 1번, 품질 2 유지, 공법 이름 변경 |
| 숙련 경험치 + 10 | 0 → 10 |
| 변경 이력 | 5건 기록 |

한계: 옵션 설명의 수치 자리는 `N`으로만 표시한다(실제 수치 계산은 하지 않음). 플레이어의 시작 공법처럼 옵션이 없는 공법은 옵션 편집 대상이 없다. 공법 경지 변경과 공법 지급은 넣지 않았다.

## 8. 대경지 돌파 검증과 난관 기운 수정 (2026-10-12)

### 대경지 돌파 — 지원하지 못함

연기 후기에서 수련치를 요구량(2346)까지 채운 상태로 축기 돌파를 시도했다.

| 시도 | 결과 |
|---|---|
| `g.conf.roleGrade`의 축기 행 확인 | 축기 초기는 돌파 품질별로 행이 셋이다(id 4·5·6). 필요 재료(`growItemRequire`, 예: 6품~1품 축기단), 재료 수(`growItemNum` 1·3·6), 천재지보 칸(`materialsNum`), 역천개명 선택 수(`fateNum` 1·2·3), 성공 시 수명 +480과 도점이 정해져 있다 |
| `UnitActionRoleUpGrade.GetCompleteRate(unit, 재료)` | 재료 없음 0, 6품 축기단 1개 30. 성공률이 있는 돌파다 |
| `unit.CreateAction(new UnitActionRoleUpGrade(4, [축기단], []))` | 반환값 2, 행동의 `state` 2. **경지가 바뀌지 않고 재료도 소모되지 않았다** |
| `UnitActionRoleUpGrade.ActionUpGradeComplete(unit, 축기 행, true)` | 호출해도 경지·능력치·기운이 변하지 않았다 |

소경지와 달리 대경지 돌파는 행동 하나를 호출해서는 진행되지 않는다. 게임에서는 역천개명 화면에서 재료를 넣고 진행하는 절차이며, 성공률 판정과 역천개명 선택이 그 안에 있다. 그 절차를 코드에서 어떻게 시작하는지는 찾지 못했다. 편집기는 대경지 돌파를 계속 막아 둔다.

실패했을 때 붙는 기운(109 "기식 문란": 공격력 -10%, 돌파 불가)과 병목 기운(120·121·122 "난관 봉착")의 내용은 설정 표에서 확인했다.

### 난관 기운이 남던 결함 — 수정

위 검증 중에 편집기의 결함을 찾았다. 수련치를 단계 요구량까지 채우면 게임이 "난관 봉착" 기운을 붙이는데, 편집기의 돌파는 게임의 난관 돌파 과정을 거치지 않으므로 이 기운이 다음 경지로 넘어간 뒤에도 남았다. 그 상태에서는 `AddExp`가 0을 돌려주고 수련치가 더 오르지 않는다.

수정: `EditService`가 수련치를 채우기 전과 돌파한 직후에, 현재 경지 행의 `lockFeature`에 해당하는 기운이 남아 있으면 `UnitActionLuckDel`로 지우고 변경 이력에 남긴다.

검증: 편집기에서 수련치 채우기 → 돌파(연기 중기 → 후기) → 다시 수련치 채우기를 눌렀을 때 수련치가 1600에서 2346까지 올랐고 난관 기운이 남지 않았다. 수정 전에는 마지막 단계에서 1600에 멈췄다.

이 결함은 v0.1 첫 검증에서 잡지 못했다. 돌파 직후의 값만 확인하고 그다음 수련치 채우기까지는 눌러 보지 않았기 때문이다.

## 9. 대경지 돌파 — 게임의 돌파 화면으로 연결 (2026-10-12)

8절의 결론("행동 호출로는 진행되지 않음")에 이어, 게임의 돌파 화면을 직접 열어 절차를 끝까지 따라갔다.

### 게임의 실제 절차 (실측)

1. `g.ui.OpenUI(UIType.UpGrade)`로 돌파 화면(`UIUpGrade`)이 열린다. 소개 연출 뒤 돌파 방식 카드가 나온다. 축기는 인도·지도·천도 세 장이다.
2. 카드를 고르면 "천재지보"와 "필요 재료" 칸이 나오고, `자동 투입`으로 가진 재료가 들어간다. 카드에 성공 확률이 표시된다.
3. 화면의 처리 메서드 `UIUpGradeGradeList.OnUpGradeClick(카드, 경지 행)`이 돌파를 시작한다. 천둥 연출이 나온다.
4. 확률 판정에 실패하면 "천겁" 장면으로 넘어가고, "목숨을 걸고 천겁과 맞선다"를 고르면 전투로 이어진다.

재료별 성공 확률(`UnitActionRoleUpGrade.GetCompleteRate`, 인도 축기 기준, 재료 1개): 6품 축기단 30, 4품 축기단 50, 1품 축기단 80.

8절에서 `UnitActionRoleUpGrade`를 직접 만든 것이 아무 효과가 없었던 이유는, 돌파가 이 화면의 절차(연출, 확률 판정, 실패 분기) 안에서 진행되기 때문이다.

### 편집기의 처리

성공 확률 판정과 실패 시의 천겁 전투는 게임의 절차이므로 편집기가 대신하지 않는다. 경지 탭은 다음이 대경지일 때 아래를 보여 준다.

| 요소 | 동작 |
|---|---|
| 돌파 방식 목록 | `ConfRoleGrade.GetGradeUpQuality(다음 대경지)`의 행마다 이름, 필요 재료와 개수, 역천개명 선택 수 |
| `재료 지급` | 그 방식의 필요 재료 후보 중 표의 마지막 것(축기단은 1품)을 필요한 개수만큼 지급. `EditService.GiveItem`을 거치므로 백업·이력이 남는다 |
| `게임의 돌파 화면 열기` | 수련치가 가득한지 확인하고, 남은 난관 기운을 지운 뒤, 편집기를 닫고 `UIType.UpGrade`를 연다 |

검증: 편집기로 연기 후기·수련치 2346까지 올린 뒤 대경지 영역이 나타났고(인도: 1품 축기단 1개·역천개명 1개, 지도: 목영기 3개·2개, 천도: 목영기 6개·3개), `재료 지급`으로 1품 축기단이 1개 들어왔으며, `게임의 돌파 화면 열기`로 편집기가 닫히고 게임의 돌파 화면이 열렸다.

확인하지 못한 것:

- 편집기로 연 화면에서 돌파를 **성공**까지 진행한 결과(성공 시의 역천개명 선택, 능력치 적용). 조사 실행에서는 30% 판정에 실패해 천겁 장면까지만 봤고, 전투는 치르지 않았다.
- 지도·천도 방식의 재료(영기류)는 "표의 마지막 후보"를 주는데, 방식에 따라 서로 다른 종류를 섞어야 하는지는 확인하지 못했다.
- 천재지보 칸의 재료는 지급하지 않는다.
- 축기 외의 대경지(결정, 금단 등)는 시험하지 않았다.

## 10. 기운 탭 (2026-10-12 추가)

편집 대상(플레이어 또는 NPC)의 기운을 보여 주고, 기운을 추가하거나 편집기로 추가한 기운을 지운다.

| 기능 | 쓰기 경로 | 규칙 |
|---|---|---|
| 기운 추가 | `unit.CreateAction(new UnitActionLuckAdd(id))` | 후보는 선천(`type` 1)과 역천개명(`type` 3) 중 숨김이 아니고 품질(`level`)이 1 이상인 것. 경지의 난관·돌파 실패 기운은 제외. 이름·효과로 검색 |

실측:

| 시험 | 결과 |
|---|---|
| "저돌"(공격력 +6, 방어력 -4) 추가 | 적용값이 공격 28 → 34, 방어 9 → 5. **기운의 효과가 능력치에 즉시 반영된다** |
| 같은 기운을 다시 추가 | 중복으로 붙지 않는다 |
| 기한이 있는 기운("기식 문란", 12) 추가 | 기한 12로 붙고 공격 -10% 반영(탐침에서만 확인. 편집기 후보에는 없음) |
| 저장 후 재시작 | 기운과 효과가 유지되고, 편집기 기록도 남아 삭제 버튼이 켜져 있음 |
| 삭제 | 능력치가 공격 28, 방어 9로 돌아옴 |

후천(`type` 2) 분류를 후보에서 뺀 이유: 이 분류에는 "도심승화", "난관 봉착", "한 가닥 원혼" 같은 게임의 상태 표식이 섞여 있다. 첫 구현에서는 후천 기운이면 모두 삭제 버튼이 켜져 "도심승화"도 지울 수 있었고, 이를 화면에서 확인한 뒤 "편집기가 추가한 것만 삭제"로 좁혔다.

한계: 후천 기운 가운데 편집기로 붙여도 되는 것을 가려내지 못해 통째로 뺐다. 게임이 붙인 불이익 기운(예: 돌파 실패의 "기식 문란")을 지우는 기능도 없다. 선천 분류의 기운을 후천 목록에 추가하는 것이므로, 게임의 "선천 기운 3개" 같은 규칙과는 별개로 동작한다.

- 구독은 무적이나 배율이 켜져 있을 때만 한다. `ModMain.Init`마다 구독 상태를 다시 맞추고 `Destroy`에서 해제한다.

확인하지 못한 것:

- 달이 넘어가는 날짜 진행(월말 처리)은 시험하지 않았다. 1일 진행만 확인했다.
- 이동할 수 없는 칸(지도 밖 등)에 대해 `IsCreateAction`이 0이 아닌 값을 주는지는 시험하지 않았다.
- 보호막 피해, 효과(지속) 피해는 별도 이벤트(`UnitHitDynIntHandlerShield`, `UnitEffectHitDynIntHandler`)라 무적의 대상이 아닐 수 있다. 일반 타격만 확인했다.
- 세이브에 진입할 때 이벤트 관리자가 새로 만들어지는지는 확인하지 못했다. 그래서 `Init`마다 다시 구독한다. 이 처리 때문에 구독이 중복되는지도 확인하지 못했다(배율이 두 번 곱해지는 증상은 시험에서 나타나지 않았다).
- 선택한 NPC에게 이동은 버튼이 켜지는 것만 확인하고 누르지는 않았다.

4단계 가운데 NPC 생성·삭제와 문파 직위 변경은 넣지 않았다.

- 이름이 같은 세부 분류는 `이름#번호`로 구분한다(예: `도구#801`).
- 실제 마우스 휠과 막대 끌기는 시험하지 못했다. 휠은 개발 도구가 보낸 스크롤 이벤트로만 확인했다.
- 한글 입력기(IME)로 검색 칸에 직접 입력하는 것은 시험하지 못했다. 개발 명령으로 값을 넣어 확인했다.
- 설명 칸 높이를 마지막에 70에서 92로 키운 뒤에는 화면을 다시 확인하지 않았다.

## 15. 능력치 분류 탭, 수량 버튼, 운명 편집 검토 (2026-10-12)

### 능력치 탭

게임 인물 화면(속성)의 다섯 분류와 같은 탭으로 나눴다. 이름과 순서도 그 화면을 따른다.

| 분류 | 항목 |
|---|---|
| 개인 속성 | 수명(년), 기분·건강·정력·체력·영력·집중력 상한, 행운, 오성, 매력, 명성, 수도 점수 |
| 전투 속성 | 공격력, 방어력, 각력, 공법 내성, 영근 내성, 회심, 호심, 이동속도, 치명타 배수(%), 치명타 저항 배수(%) |
| 공법 자질 | 도법, 창법, 검법, 권법, 장법, 지법 |
| 영근 자질 | 화·수·뇌·풍·토·목영근 |
| 기예 | 연단, 연기, 풍수, 부적, 약재, 광재 |

- 매력·명성·수도 점수는 게임 화면에서 다섯 분류 밖(인물 정보)에 있다. 편집기에서는 개인 속성에 두었다.
- 부적(`PropertyData.symbol`)을 새로 넣었다. 상한표에 부적 항목이 없어 풍수의 범위를 빌려 쓰고 "자체 상한"으로 표시한다.
- 게임 화면의 `체력 303/450`은 현재값/상한이다. 편집기의 "체력 상한"이 뒤의 숫자다(실측: `hpMax` 450).
- 게임 화면에 나오는 값은 저장값이 아니라 보정이 더해진 값이다(예: 도법 저장 2, 화면 22). 열 이름을 "게임 화면 값(보정 포함)"으로 바꿨다.
- 사용자의 게임 화면 캡처와 대조해 개인·전투·공법 자질·기예의 화면 값이 모두 일치함을 확인했다. 영근 자질 탭은 화면을 캡처만 하고 대조하지 않았다.
- "공법 내성"=`phycicalFree`, "영근 내성"=`magicFree`의 대응은 확인하지 못했다. 시험 인물의 값이 둘 다 0이라 화면으로 구분되지 않는다.

### 수량 선택

단위를 한 버튼으로 돌려 가며 바꾸던 것을 `1 / 10 / 100 / 1000` 버튼과 직접 입력 칸(1~999999, "적용")으로 바꿨다. 자원 탭에서는 영석 추가량과 아이템 지급 수량을 따로 고른다. 능력치 증감 단위 등 다른 탭의 단위도 같은 모양으로 바꿨다.

실측: 아이템 지급 수량 100 선택 시 표의 버튼이 "지급 x100"으로 바뀜. 영석 추가량에 250을 입력해 적용하고 추가 → 501 → 751.

### 운명(선천·후천) 추가·수정·삭제 검토

게임 화면의 "선천운명"은 `PropertyData.bornLuck`(배열), "후천운명"은 `PropertyData.addLuck`(목록)이다. 편집기의 기운 탭이 다루는 것과 같은 데이터다.

실험(시험 인물 선천 `[2804, 1526, 2010]`, 저장하지 않음):

| 실험 | 결과 |
|---|---|
| 후천운명 삭제 `UnitActionLuckDel(9000002)` | `addLuck`에서 빠지고 적용 중인 운명 수 6 → 5 |
| 후천운명 추가 `UnitActionLuckAdd(9000002)` | `addLuck`에 다시 들어가고 6으로 복귀 |
| 선천운명 삭제 `UnitActionLuckDel(1526)` | 반환 0. **`bornLuck`는 그대로인데 적용 중인 운명 수만 6 → 5.** 저장 데이터와 적용 상태가 어긋난다 |
| 그 선천운명을 다시 추가 `UnitActionLuckAdd(1526)` | 선천이 아니라 `addLuck`에 들어간다(선천과 후천에 같은 번호가 함께 있게 됨) |

판단:

- 후천운명의 추가·삭제는 게임의 행동으로 된다. 지금 편집기는 추가 후보를 선천·역천개명 분류로, 삭제를 편집기가 추가한 것으로 제한하고 있다. 이 제한을 풀지는 정책 문제다(후천 분류에 "도심승화" 같은 게임 상태 표식이 섞여 있다).
- 선천운명의 삭제·교체는 게임의 행동으로는 되지 않는다. `bornLuck` 배열을 직접 고쳐 쓰고 적용 중인 운명을 다시 만들게 해야 하는데, 다시 만드는 경로는 확인하지 못했다. 저장 후 다시 불러오면 반영되는지도 시험하지 않았다.
- "수정"에 해당하는 게임 기능은 찾지 못했다. 삭제 후 추가로 대신해야 한다.

## 16. 운명 탭 — 후천운명 제한 해제, 선천운명 교체 (2026-10-12)

탭 이름을 게임 표기에 맞춰 "기운"에서 "운명"으로 바꿨다. 10절의 제한 두 가지를 풀고 선천운명 교체를 넣었다.

| 기능 | 쓰기 경로 | 규칙 |
|---|---|---|
| 후천운명 추가 | `UnitActionLuckAdd(id)` | 후보는 선천·후천·역천개명 분류 전체(숨김만 제외). 품질 0 이하도 포함. 경지의 난관·돌파 실패 운명은 "경지 진행 표식"으로 표시 |
| 후천운명 삭제 | `UnitActionLuckDel(id)` | 편집기가 추가한 것은 바로, 게임이 붙인 것은 "정말 삭제"를 한 번 더 눌러야 지운다 |
| 선천운명 교체 | `LuckService.ReplaceBorn` | 아래 순서 |

선천운명 교체 순서: `UnitActionLuckDel(옛 번호)`로 적용 중인 효과를 끄고 → `bornLuck[자리].id`에 새 번호를 쓰고 → `UnitActionLuckAdd(새 번호)`로 효과를 켜고 → 그 행동이 후천 목록에 넣은 항목을 `PropertyData.DelAddLuck(새 번호)`로 뺀다.

실측(시험 인물 선천 `[2804, 1526, 2010]`, 공격 23/28, 방어 9/9):

| 시험 | 결과 |
|---|---|
| `bornLuck[1].id = 1201`(저돌)만 쓰기 | 그 자리에서는 능력치 변화 없음 |
| 위 상태로 저장 후 재시작 | 선천 `[2804, 1201, 2010]` 유지, 공격 34, 방어 5. **저장 데이터만 고쳐도 다시 불러오면 적용된다** |
| 편집기의 교체(육근청정 → 저돌) | 재시작 없이 선천 `[2804, 1201, 2010]`, 후천 목록 변화 없음, 적용 중 운명 수 6 유지, 공격 34, 방어 5 |
| 게임이 붙인 후천운명(도심승화)의 삭제 버튼 | 첫 클릭에 확인 문구와 "정말 삭제"로 바뀜(실제 삭제는 하지 않음) |
| 후천 분류에서 추가("한 가닥 원혼") 후 삭제 | 후천 목록에 들어갔다가 빠짐 |

이 실험은 사용자의 세이브에서 했다. 실험 전 세이브 폴더를 `.devremote/save-backup-20261012-born`에 복사했고, 저장이 필요한 시험 뒤에 그 복사본으로 되돌려 파일이 모두 같음을 확인했다.

확인하지 못한 것, 한계:

- 편집기의 교체로 바꾼 상태를 저장 후 다시 불러오는 것은 시험하지 않았다(저장 데이터가 위 두 번째 시험과 같은 모양이라 같을 것으로 본다).
- 선천운명의 추가(칸 늘리기)와 삭제(칸 줄이기)는 넣지 않았다. `bornLuck` 배열의 길이를 바꿔야 하고 시험하지 않았다.
- 식혼검처럼 게임 시작 조건과 묶인 선천운명을 바꿨을 때의 영향은 시험하지 않았다.
- 후천 분류 후보에는 "한 가닥 원혼" 같은 불이익·상태 운명이 그대로 나온다. 경고 문구만 있고 막지는 않는다.
- NPC를 대상으로 한 교체는 시험하지 않았다.

## 17. 운명이 게임 화면에 나오는 조건, 선천운명 추가·삭제 (2026-10-12)

사용자 보고: 편집기로 추가한 "검마환생" 등 여섯 개가 효과는 적용되는데 게임 인물 화면의 후천운명 칸에 나오지 않고, 세이브를 다시 불러와도 같다.

실측(여섯 개는 모두 선천 분류 `type` 1이고 `addLuck`에 들어 있었다):

| 시험 | 게임 인물 화면 |
|---|---|
| 후천 분류(`type` 2) "도심응결"을 `addLuck`에 추가 | 후천운명 칸에 나온다 |
| 역천개명 분류(`type` 3) "도심약유"를 `addLuck`에 추가 | 선천·후천 어느 칸에도 나오지 않는다 |
| 선천 분류(`type` 1)가 `addLuck`에 있는 상태 | 어느 칸에도 나오지 않는다 |
| 그 항목을 `bornLuck`로 옮김 | 선천운명 칸에 나온다. 여덟 개까지 세로로 늘어나는 것을 확인 |

결론: 인물 화면의 선천운명 칸은 `bornLuck`를, 후천운명 칸은 `addLuck` 가운데 후천 분류만 보여 준다. 16절의 "어느 분류든 후천 목록에 추가"는 선천·역천개명 분류에서 화면에 나오지 않는 운명을 만든다.

고친 것:

| 기능 | 쓰기 경로 |
|---|---|
| 선천운명 추가 (`LuckService.AddBorn`) | `UnitActionLuckAdd(id)`로 효과를 켜고, 게임이 `addLuck`에 만든 항목(`LuckData`)을 한 칸 늘린 `bornLuck` 배열로 옮긴 뒤 `DelAddLuck(id)`. 이미 `addLuck`에 있는 운명은 그 항목을 옮기기만 한다 |
| 선천운명 삭제 (`LuckService.RemoveBorn`) | `UnitActionLuckDel(id)`로 효과를 끄고 `bornLuck` 배열에서 그 자리를 뺀다. 항상 한 번 더 확인한다 |

- 운명 추가 화면에서 선천 분류는 "선천운명에 추가", 후천 분류는 "후천운명에 추가"가 된다. 역천개명 분류는 후천 목록에 붙고 화면에 나오지 않는다는 안내가 붙는다.
- 운명 목록의 "게임 화면의 위치" 열에 선천운명 / 후천운명 / 표시 안 됨(효과만)을 보여 준다. 표시 안 되는 선천 분류 운명에는 "선천으로 옮김" 버튼이 있다.

실측(시험 인물 선천 3개, 후천 목록에 환생 계열 6개):

| 시험 | 결과 |
|---|---|
| "선천으로 옮김" 6회 | `bornLuck` 9개, `addLuck`에서 6개 빠짐, 적용 중 운명 수 12 유지, 능력치 변화 없음 |
| 선천운명 "장마환생" 삭제 | `bornLuck` 8개, 적용 중 11, 공격 37 → 36 |
| 저장 후 재시작 | `bornLuck` 8개 유지, 능력치 유지, 인물 화면 선천운명 칸에 8개 표시, 장법 135 → 110 |

시험은 사용자의 세이브에서 했고, 시험 전 복사본(`.devremote/save-backup-20261012-born2`)으로 되돌려 파일이 모두 같음을 확인했다.

확인하지 못한 것:

- 운명 추가 화면의 "선천운명에 추가" 버튼(후천 목록에 없던 운명을 새로 추가하는 경로)은 눌러 보지 않았다. "선천으로 옮김"과 같은 함수의 다른 갈래다.
- 역천개명 분류의 운명을 게임이 어디에 보여 주는지는 찾지 못했다.
- 선천운명이 몇 개까지 화면에 들어가는지, 게임의 다른 기능이 늘어난 배열을 어떻게 다루는지는 시험하지 않았다.

## 18. 역천개명 분류의 운명이 표시되는 곳 (2026-10-12 조사)

역천개명 분류(`ConfRoleCreateFeatureItem.type` 3)의 운명은 인물 화면의 운명 칸이 아니라 **경지 화면(`UIType.FateFeature`)의 경지별 쪽**에 나온다. 축기경부터 각 경지 쪽에 "역천개명" 제목이 있고, 그 아래에 그 경지에서 얻은 역천개명 하나가 표시된다.

표시는 운명 목록이 아니라 경지별 기록을 읽는다.

| 대상 | 기록 위치 | 모양 |
|---|---|---|
| 플레이어 | `g.data.world.playerLog.upGrade` | `Dictionary<int, DataWorld.World.PlayerLogData.GradeData>` — 키는 대경지 번호(`ConfRoleGradeItem.grade`), 값은 `quality`와 `luck`(운명 번호) |
| NPC | `unit.data.unitData.npcUpGrade` | 같은 모양 |

역천개명으로 뽑을 수 있는 운명과 경지 범위는 `g.conf.fateFeature`(`ConfFateFeatureItem.gradeMin`·`gradeMax`·`group`·`mutexGroup`, 203개)에 있다. 번호는 `ConfRoleCreateFeatureItem`의 번호와 같다.

실측:

| 시험 | 경지 화면 |
|---|---|
| 대경지 28의 NPC 데이터 | `addLuck`에 역천개명 분류 6개, `npcUpGrade`에 `{2: luck=700164, 3: 700183, 4: 700026, 5: 700019, 6: 700040, 7: 700065}` — 경지마다 하나씩, `addLuck`의 것과 같은 번호 |
| 플레이어(연기 후기)에 `UnitActionLuckAdd(700042)`만 | 연기경·축기경 쪽 어디에도 나오지 않음. `playerLog.upGrade`는 비어 있음 |
| `UnitActionLuckAdd.fateFeatureGrade = 2`를 지정해 추가 | 변화 없음(기록이 생기지 않는다) |
| 경지를 시험으로 축기 초기로 올림(`SetGradeID(4)`) | 축기경 쪽에 "역천개명" 제목만 나오고 비어 있음 |
| `playerLog.upGrade[2] = { quality = 0, luck = 700042 }`를 직접 씀 | 축기경 쪽 "역천개명" 아래에 "투화중소"가 표시됨 |

결론: 역천개명이 화면에 나오려면 (1) 그 운명이 `addLuck`에 있어 효과가 적용되고 (2) 경지별 기록의 `luck`에 번호가 있어야 하며 (3) 그 경지에 도달해 있어야 한다. 경지 하나에 하나만 기록된다. 편집기의 "역천개명 분류 추가"는 (1)만 하므로 효과만 적용되고 표시되지 않는다.

확인하지 못한 것:

- `GradeData.quality`의 뜻(NPC 기록에서 5와 0이 번갈아 나온다). 값을 잘못 쓰면 무엇이 달라지는지 시험하지 않았다.
- 도달하지 않은 경지의 기록을 미리 써 두면 나중에 게임의 돌파 과정이 덮어쓰는지.
- 기록만 있고 `addLuck`에는 없는 경우의 표시와 효과.
- 저장 후 다시 불러와도 기록이 유지되는지(시험은 저장하지 않고 끝냈다).

조사에 쓴 개발 명령: `fatelist <경지>`, `fateadd <번호> <경지>`, `luckdump <단위>`, `findfated`, `gradelog [경지 번호 품질]`.

## 19. 역천개명 (경지별) 지정 (2026-10-12 추가)

운명 탭 아래의 "역천개명 (경지별)" 화면. 편집 대상이 도달한 경지(축기경부터)마다 한 줄이 나오고, "정하기"/"변경"으로 그 경지의 역천개명을 고른다.

| 기능 | 쓰기 경로 | 규칙 |
|---|---|---|
| 역천개명 정하기·변경 (`FateService.Set`) | 이전 것이 있으면 `UnitActionLuckDel(옛 번호)` → `UnitActionLuckAdd(새 번호)` → 경지별 기록의 `luck`에 새 번호 | 도달한 경지만. 후보는 `g.conf.fateFeature`에서 그 경지가 `gradeMin`~`gradeMax`에 드는 것. 이미 가진 운명은 고를 수 없다 |

- 경지별 기록은 플레이어가 `g.data.world.playerLog.upGrade`, NPC가 `unitData.npcUpGrade`다(18절).
- 기록이 이미 있으면 `luck`만 바꾸고 `quality`는 건드리지 않는다. 기록이 없으면 `quality = 0`으로 새로 만든다.
- 일반 "운명 추가"의 역천개명 분류는 그대로 두었다. 그쪽으로 붙이면 효과만 적용되고 경지 화면에 나오지 않는다는 안내를 붙였다.

실측(시험 인물 연기 후기, 경지별 기록 없음):

| 시험 | 결과 |
|---|---|
| 연기 후기 상태에서 화면 열기 | "아직 축기경에 이르지 않았습니다" 안내, 줄 없음 |
| 시험으로 경지를 축기 초기로 올린 뒤(`SetGradeID(4)`) 축기 줄 "정하기" → 첫 후보 | 기록 `{2: quality=0, luck=700001}`, `addLuck`에 700001 추가 |
| 같은 줄 "변경" → 다른 후보 | 기록 `{2: luck=700004}`, `addLuck`에서 700001이 빠지고 700004가 들어감, 적용 중 운명 수 유지 |
| 저장 후 재시작 | 기록과 `addLuck` 유지. 게임 경지 화면의 축기경 쪽 "역천개명" 아래에 "국화탕" 표시 |

시험은 사용자의 세이브에서 했고, 시험 전 복사본(`.devremote/save-backup-20261012-fate`)으로 되돌렸다.

확인하지 못한 것, 한계:

- `GradeData.quality`의 뜻. 기록이 없던 경지에 0으로 새로 만드는 것이 맞는지 모른다. 게임에서 실제로 돌파한 경지에는 게임이 만든 기록이 있을 것이므로 그 값은 보존된다.
- 게임에서 실제로 돌파해 생긴 기록을 바꾸는 경우(시험은 편집기가 만든 기록으로만 했다).
- `ConfFateFeatureItem.group`·`mutexGroup`(같은 계열, 함께 가질 수 없는 계열)과 `condition`은 검사하지 않는다.
- 역천개명을 비우는 기능은 없다.
- NPC 대상은 시험하지 않았다.
- 도달하지 않은 경지는 정할 수 없게 막았다. 미리 써 둔 기록을 게임의 돌파 과정이 어떻게 다루는지 시험하지 않았기 때문이다.

### 대경지 7·8의 천재지보

- 편집기는 천재지보를 지급했다(화신: 蕴仙芝 등 4종, 편집기 메시지와 게임의 도구 선택 창에서 확인).
- 게임의 `자동 투입`은 이 경지의 천재지보를 넣지 않는다. 빈 칸을 누르면 열리는 "도구 선택" 창에는 지급한 4종이 후보로 나온다.
- 설정 표 `ItemRarityMaterials`에서 대경지 2~6의 천재지보는 `effect`에 능력치 보정이 적혀 있고(`atk_4|def_3|...`), 대경지 7·8의 것은 `effect`가 `0`이다. 자동 투입이 넣지 않는 이유는 이 차이로 추정한다(확인하지 못함).
- 도구 선택 창에서 직접 골라 넣는 것은 확인하지 못했다. 개발용 원격 클릭으로는 선택 표시가 바뀌지 않았다. 실제 마우스로는 시험하지 못했다.

### 그 밖에 드러난 것

- 가방이 가득 차면 지급이 되지 않는다. 편집기는 "일부가 지급되지 않았습니다"라고 알린다. 시험을 이어 하며 재료가 쌓였을 때 화신에서 처음 나타났다.
- 한 번은 돌파 화면을 거친 뒤 게임 메뉴(돌아가기·저장…)가 떠 있고 편집기 단축키가 듣지 않는 상태가 됐다. 게임을 다시 띄운 뒤 같은 순서로 시험했을 때는 단축키가 정상이었고, 재현하지 못했다.

조사에 쓴 개발 명령: `editor`(단축키 없이 편집기 열기), `closeui`(돌파 화면 닫기).

### 주의할 점

- 조합 번호(`ConfBattleSkillCombine` 등)는 개별 기술이 아니라 뽑기 묶음이다(무예 4144개, 신법 1051개, 심법 2741개). 묶음에 이름이 없고, 같은 번호라도 뽑힐 때마다 결과가 달라질 수 있다. 편집기에서 "이름으로 골라 추가"하려면 `baseID`별 목록(이름을 가진 설정)을 따로 찾아야 한다. 아직 찾지 못했다.
- 종류와 맞지 않는 조합을 주면 깨진 기술이 들어간다. `SkillRight`·`Ultimate`에 무예 조합을 주었을 때 이름 없는 항목이 생겼고(예외가 났는데도 목록에 남음), 그 항목은 번호로 지우는 행동에서 예외가 났다.
- 수련과 참오는 편집기에 이미 대응 기능이 있다. 공법 탭의 "숙련 경험치 +"(`AddMartialExp`)가 수련의 결과에, 옵션 교체·품질 설정이 참오의 결과에 해당한다.

### 확인하지 못한 것

- 절기·신통에 맞는 조합 번호와 화면 탭 대응.
- 약재 탭(약보)의 서적 아이템 분류와 학습.
- 기예 항목의 삭제 경로(목록에서 번호를 빼면 되는지).
- 수련·참오 행동이 불가(3)로 나오는 조건.
- NPC 대상.

조사에 쓴 개발 명령: `skconf`, `sklist`, `sknew`, `sklearn`, `sklearn2`, `skdel`, `skdel2`, `skdel3`, `sktrain`, `skrealize`, `skequip`, `skunequip`, `arts`, `pillstudy`, `artstudy`.

## 23. 기예 탭, 공법 탭의 기술 추가·장착·망각 (2026-10-12 추가)

22절의 조사 결과로 세 가지를 넣었다. 탭 순서는 능력치·자원·경지·공법·운명·기예·NPC·세계·안전이 됐다.

### 기예 탭

게임 기예 화면의 여섯 탭과 같은 분류로, 그 분류의 서적을 표로 보여 주고 "배우기"/"잊기"를 한다. 기록이 세계 데이터에 있어 편집 대상과 무관하게 플레이어의 기록을 바꾼다.

| 탭 | 서적(`ItemProps.className`) | 배우기 | 잊기 |
|---|---|---|---|
| 연단 | 단방 605 | `UnitActionPropPillFormulaStudy` | `g.data.world.pillFormulas`에서 제거 |
| 연기 | 연기보 618 | `UnitUnitArtistrySkillStudy` | `g.data.world.allArtistrySkillID`에서 제거 |
| 부적 | 부적 도보 658 | 같음 | 같음 |
| 풍수 | 풍수서 614 | 같음 | 같음 |
| 약재 | 약보 615 | 같음 | 같음 |
| 광재 | 감식서 617 | 같음 | 같음 |

- "모두 배우기"는 더 배워지는 것이 없을 때까지 최대 8번 되풀이한다.
- 잊기는 게임에 없는 기능이라 기록 목록에서 직접 뺀다. 한 번 더 확인한다.

실측: 단방 1개 배우기(연단 1/168), 약보 1개 배우기(약재 1/72), 풍수 모두 배우기 → 7개 배움·28개는 게임이 거부, 풍수서 1개 잊기 → `allArtistrySkillID`에서 빠짐.

풍수서는 기술 7종에 단계가 다섯씩(1·2·3·4·종) 있고, 모두 배우기를 되풀이해도 1단계 7개만 배워졌다. 2단계 이상이 거부되는 조건은 찾지 못했다.

### 공법 탭 — 기술 추가

"기술 추가" 화면에서 게임 기술 화면의 다섯 분류, 경지(1~10), 이름으로 골라 배운 상태로 넣는다(`SkillCatalog`).

| 분류 | `MartialType` | 목록 | 뽑기 묶음 |
|---|---|---|---|
| 무예/영술 | `SkillLeft` | `g.conf.battleSkillAttack`의 `type` 1·2 | `GetSkillReward(101, 경지)` |
| 절기 | `SkillRight` | 같은 표의 `type` 3 | `GetSkillReward(102, 경지)` |
| 신법 | `Step` | `g.conf.battleStepBase` | `GetStepReward(101, 경지)` |
| 심법 | `Ability` | `g.conf.battleAbilityBase` | `GetAbilityReward(101, 경지)` |
| 신통 | `Ultimate` | `battleSkillAttack`의 `type` 4 | `GetSkillReward(103, 경지)` |

- 목록에는 `gradeMax`가 1 이상인 것만 넣는다. 0~0인 항목(무예 표에만 1300여 개)은 플레이어가 배우는 기술이 아니다.
- 추가: 원하는 기술 번호가 나올 때까지 묶음에서 다시 뽑아(최대 3000번) 게임이 정한 옵션이 붙은 공법을 만들고, `DataProps.PropsData.NewMartial` → `unitData.StudyActionMartialProp`로 배운 상태가 되게 한다. 끝내 나오지 않으면 옵션 없는 값(`2,0,1,종류,번호,경지`)으로 만든다.
- 만든 공법의 `martialInfo`가 비어 있거나 번호가 다르면 배우게 하지 않는다. 첫 구현에서 이 확인 없이 `gradeMax` 0인 항목을 넣었다가 이름 없는 깨진 기술이 생겼다.
- 선택한 경지가 기술의 `gradeMin`~`gradeMax` 밖이면 버튼이 막힌다.

실측(경지 3): 절기 "광혈참"·"노혈참", 신법 "약"·"돌", 심법 "경"·"공", 신통 "마살도"·"패도참"이 옵션 낱말이 붙은 이름으로 들어갔고, 게임 기술 화면의 절기·신법·심법·신통 탭에 각각 표시됐다. 무예/영술의 첫 두 줄은 경지 1 전용이라 경지 3에서는 막혔다(22절에서 `SkillLeft`가 무예/영술 탭에 나오는 것은 확인).

### 공법 탭 — 장착·해제·망각

| 기능 | 경로 |
|---|---|
| 장착 | `UnitActionMartialEquip(ActionMartialData, 칸)`. 심법은 `abilitys`의 빈 칸 가운데 첫 칸, 나머지는 0 |
| 장착 해제 | `UnitActionMartialUnequip(ActionMartialData)` |
| 기술 망각 | `UnitActionMartialDel(ActionMartialData)`. 한 번 더 확인한다 |

실측: 신법 "탈의약" 장착 → `step`에 들어가고 목록에 "장착 중", 해제 → 비워짐, 망각 두 번 클릭 → 익힌 목록에서 빠짐.

공법 종류 표기를 게임 화면에 맞췄다(무예/영술·절기·신법·심법·신통). 수련과 참오는 게임 행동이 불가로 나와(22절) 넣지 않았고, 숙련 경험치·옵션 품질·교체가 그 결과를 대신한다고 화면에 적었다.

### 확인하지 못한 것

- 이번 구현(편집기 버튼)으로 바꾼 상태의 저장 후 재시작. 같은 경로를 개발 명령으로 쓴 경우는 22절에서 확인했다.

- 기예 잊기 뒤 게임 화면 표시와 저장.
- 연기·부적·광재의 "모두 배우기".
