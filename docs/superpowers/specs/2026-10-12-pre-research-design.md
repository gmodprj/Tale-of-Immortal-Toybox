# GGBH Cheat Sandbox 사전 조사 — 설계 스펙

> 작성일: 2026-10-12
> 대상 게임: 鬼谷八荒(Tale of Immortal), 설치 경로 `E:\Games\Tale of Immortal`
> 작업 폴더: `E:\TlToybox`

## 1. 목적

최종 목표는 귀곡팔황의 플레이어·NPC·아이템·경지·공법·관계·문파·세계·전투 데이터를
조회·편집하는 통합 치트·샌드박스 모드 `GGBH Cheat Sandbox`다(기준 문서:
`docs/00-design-brief.md`).

이 스펙은 그 모드의 v0.1 이전 단계인 **사전 조사**만 다룬다. 기준 문서의 기술 가정과
창작마당 후보 목록은 미검증 상태이며, 이번 작업이 그 공백을 실측값으로 채운다.

## 4. 결정 사항

- **최종 목표**: 통합 치트·샌드박스 모드(기준 문서의 A안).
- **모드 로딩 경로**: 공식 ModMain 경로(`ModCode` + `ModExcel` + `ModAssets`, `GGBH_MOD.dll`이
  로드)를 채택한다. 독립 MelonMod와 혼합 방식은 채택하지 않는다. 공식 경로로 불가능한 기능이
  실제로 확인되기 전에는 보조 MelonMod를 추가하지 않는다.
- **경로 검증**: 위 채택은 작업 2의 판정으로 확정된다. 작업 2에서 공식 경로가 부적합하다고
  나오면 작업 3에 착수하지 않고 멈춰 보고한다.
- **작업 3의 수준**: 폴더 뼈대 + 빌드 가능한 빈 프로젝트. 게임 쪽 폴더에는 아무것도 만들지 않는다.
- **git**: 로컬 전용. 원격 저장소는 만들지 않는다.

- Unity 버전, 스크립팅 백엔드, 아키텍처
- MelonLoader 버전과 구성 요소(`Managed`, `Dependencies`, 로그)

- 확인하지 못한 항목은 "미확인"과 그 사유를 적는다. 추정값을 실측값처럼 적지 않는다.

### 6.2 작업 2 — 모드 개발 구성 리서치

**산출물**: `docs/02-mod-dev-research.md`, `docs/02a-workshop-survey.md`

**방법**: 네 가지 출처를 모두 확인한다.

1. **로컬 공식 자료** — `代码编写教程.docx`, `GGBH_API.chm`, `ModMain` 템플릿,
   `MOD模板例子`의 `ModProject` 4종, `配置修改教程`, `资源修改教程`
2. **웹** — 공식 모드 제작 가이드, GitHub에 공개된 귀곡팔황 모드 소스, 커뮤니티 위키·포럼
3. **Steam 창작마당**(appid 1468810) — 기준 문서 10장의 후보 10종 재검증,
   10.1의 키워드로 신규 경지·신규 공법·치트 계열 모드 검색
4. **모드 사이트** — Nexus Mods, 3DM 등 귀곡팔황 모드를 배포하는 사이트

**`02-mod-dev-research.md`에 담을 내용**

- 공식 ModMain 경로의 프로젝트 구조, 빌드 절차, 로드 절차, 창작마당 배포 절차

- 공식 경로에서 UI를 주입하는 방법과 한계
- 설정 테이블(`ModExcel`) 수정으로 가능한 일과 코드로만 가능한 일의 구분
- 독립 MelonMod 경로와의 비교
- **판정**: 공식 ModMain 경로가 이 프로젝트에 적합한지, 근거와 함께 명시

**`02a-workshop-survey.md`에 담을 내용**

조사한 모드마다 한 행씩, 다음 열을 기록한다.

| 열 | 내용 |
|---|---|
| 제목 | 페이지에 표시된 원문 제목 |
| ID / 링크 | Workshop ID 또는 사이트 URL |

| 기능 요약 | 페이지 설명 기준 |

| 검증 상태 | 확인 / 불일치 / 접근 불가 |
| 참고 가치 | 기준 문서의 어느 기능에 참고되는지 |

**완료 기준**

- 판정이 근거와 함께 문서화된다.
- 기준 문서 후보 10종 각각에 검증 상태가 기록된다. 제목과 ID가 기준 문서와 다르면 "불일치"로
  표기하고 실제 값을 적는다.
- 웹에서 얻은 내용에는 출처 링크가 붙는다.

**제약**

- 다른 모드의 소스 코드는 구조와 접근 방식만 참고하고 복사하지 않는다.
- 페이지에 접근하지 못했거나 내용을 확인하지 못한 항목을 확인된 것처럼 적지 않는다.

### 6.3 작업 3 — 모드 폴더 설정

**선행 조건**: 작업 2의 판정이 "공식 ModMain 경로 적합"일 것. 아니면 착수하지 않고 보고한다.

**산출물**: `src/` 아래의 빈 모드 프로젝트, `tests/` 폴더, `README.md`, `CLAUDE.md`

**방법**

- 공식 `ModMain` 템플릿의 프로젝트 구조를 따르는 빈 프로젝트를 `src/`에 만든다.
- 어셈블리 참조는 게임의 `MelonLoader/Managed`를 가리킨다. 게임 DLL을 저장소에 복사하지 않는다.
- 기준 문서 11장의 폴더(`Core`, `Adapters`, `Resolvers`, `Services`, `Features`, `UI`, `Safety`)를
  빈 상태로 만든다.
- 프로젝트 내용은 진입점 클래스 하나와 로그 출력 한 줄로 한정한다.

**완료 기준**

- 템플릿이 요구하는 빌드 도구로 빌드가 성공한다.
- 기능 코드가 없다.

**중단 지점**: 빌드 산출물을 게임 폴더로 복사하는 것과 인게임 로드 확인은 이번 범위 밖이다.
빌드 성공까지 진행하고 멈춘다.

### 6.4 작업 4 — 인게임 상태 구성 분석

**산출물**: `docs/04-ingame-state-analysis.md`

**방법**: 정적 분석만 수행한다. 다음 세 자료를 대조한다.

- `MelonLoader/Managed/Assembly-CSharp.dll`의 타입·필드·메서드 메타데이터
- `GGBH_API.chm`
- 게임 설정 테이블(작업 2에서 위치와 형식을 확인)

**분석 영역**: 기준 문서 3~9장에 대응하는 플레이어, NPC, 아이템, 경지·돌파, 공법·무공·신통,
관계, 문파, 세계·이벤트, 전투.

**기록 형식**: 영역마다 기준 문서 11.1의 조사 기록 표를 쓴다.

**완료 기준**

- 영역마다 상태를 소유하는 클래스와 주요 필드가 기록된다.
- 클래스명·필드명·메서드명은 어셈블리 또는 API 문서에서 실제로 확인한 것만 적는다.
- 정적 분석으로 확정할 수 있는 것은 "읽기 후보"까지다. 쓰기, 저장 반영, 연쇄 처리는
  "미확인(런타임 검증 필요)"로 적는다.
- 런타임 검증이 필요한 항목을 v0.1 검증 목록으로 문서 끝에 정리한다.

**제약**: 메타데이터를 추출하는 일회성 스크립트는 스크래치패드에서만 쓰고 저장소에 넣지 않는다.

## 8. git 운용

- `E:\TlToybox`를 git 저장소로 초기화한다. 원격은 없다.
- `main`은 초기 빈 커밋만 가진다. `develop`을 `main`에서 분기한다.
- 작업 브랜치는 `develop`에서 분기한다.
  - `docs/pre-research` — 이 스펙과 작업 1·2·4의 문서
  - `chore/mod-scaffold` — 작업 3
- 원격이 없어 PR을 만들 수 없으므로, 작업 브랜치는 로컬에서 merge commit으로 `develop`에
  병합한다. `main`으로의 병합은 이번 범위에서 하지 않는다.
- `.omc/`와 빌드 산출물(`bin/`, `obj/`)은 `.gitignore`에 넣는다.
